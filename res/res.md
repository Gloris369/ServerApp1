# ServerApp1

## Практична робота №1

**Тема:** Базові конструкції, структури даних та конкурентність у Go.

## Опис

ServerApp1 — консольний застосунок для перевірки доступності мережевих ресурсів за допомогою HTTP-запитів.

Програма послідовно демонструє три підходи до виконання перевірок:

1. послідовне виконання;
2. конкурентне виконання з використанням горутин, `sync.WaitGroup` та `sync.Mutex`;
3. конкурентне виконання з передачею результатів через канал `chan`.

Для кожного ресурсу визначається HTTP-статус, тривалість запиту та можлива помилка підключення.

## Використані URL

Для демонстрації роботи програми перевіряються:

```text
https://go.dev
https://github.com
https://httpbin.org/status/404
https://example.com
https://invalid-fake-host-test.org
```

Остання адреса використовується для демонстрації обробки мережевої помилки.

`https://httpbin.org/status/404` навмисно повертає HTTP 404. Така відповідь не є помилкою мережевого з'єднання, оскільки HTTP-сервер успішно відповів на запит.

## Запуск

Перейти до каталогу проєкту:

```bash
cd ServerApp1
```

Запустити програму:

```bash
go run .
```

## Перевірка на race condition

Для перевірки відсутності станів гонитви необхідно виконати:

```bash
go run -race .
```

У разі коректної роботи програми повідомлення:

```text
WARNING: DATA RACE
```

не повинно з'являтися.

## Реалізація рівня 1

На першому рівні використовується структура `CheckResult`, яка зберігає адресу ресурсу, код відповіді, текст статусу, тривалість виконання та можливу помилку.

Для абстрагування перевірки створено інтерфейс:

```go
type Checker interface {
    Check(string) CheckResult
}
```

Структура `WebChecker` реалізує цей контракт без використання ключового слова `implements`, оскільки Go використовує неявну реалізацію інтерфейсів.

Послідовний режим перевіряє адреси одну за одною.

## Реалізація рівня 2

На другому рівні кожна HTTP-перевірка запускається в окремій горутині.

Для очікування завершення всіх горутин використовується:

```go
sync.WaitGroup
```

Оскільки декілька горутин працюють зі спільною структурою `Report`, доступ до неї захищається за допомогою:

```go
sync.Mutex
```

Це дозволяє уникнути одночасної зміни спільного стану різними горутинами.

## Реалізація рівня 3

На третьому рівні результати перевірок передаються через канал:

```go
chan CheckResult
```

Горутини виконують HTTP-запити та надсилають отримані результати в канал.

Окрема горутина очікує завершення всіх перевірок через `WaitGroup`, після чого закриває канал:

```go
wg.Wait()
close(results)
```

Головна горутина отримує результати за допомогою:

```go
for result := range results
```

Після закриття каналу цикл завершується автоматично.

Такий підхід дозволяє не використовувати `Mutex` для передачі результатів і демонструє модель конкурентної взаємодії через канали.

## Перевірка відсутності стану гонитви

Для перевірки програма запускалася з Race Detector:

```bash
go run -race .
```

Очікуваний результат — виконання програми без повідомлень:

```text
WARNING: DATA RACE
```

У конкурентному режимі з `Mutex` спільний об'єкт статистики захищений критичною секцією.

У режимі з каналами результати передаються через потокобезпечний канал, а підсумкова статистика формується в головній горутині.

## Порівняння продуктивності

Послідовний режим виконує наступний HTTP-запит тільки після завершення попереднього. Через це загальний час приблизно залежить від сумарної тривалості всіх запитів.

У конкурентному режимі запити запускаються практично одночасно. Тому загальний час переважно визначається найдовшим запитом, а не сумою всіх запитів.

Для оцінки прискорення використовується співвідношення:

```text
Прискорення = час послідовного виконання / час конкурентного виконання
```

Конкретне значення прискорення змінюється при кожному запуску залежно від стану мережі.

## Висновок

У ході практичної роботи було створено консольний HTTP URL Health Checker мовою Go. У програмі реалізовано роботу зі структурами, методами, інтерфейсами та явною обробкою помилок.

Також було реалізовано конкурентне виконання HTTP-запитів за допомогою горутин та синхронізації через `sync.WaitGroup`. Для захисту спільного стану на другому рівні використано `sync.Mutex`.

На третьому рівні результати перевірок передаються між горутинами за допомогою каналів. Закриття каналу виконується після завершення всіх робочих горутин, а результати обробляються в головній горутині.

Додатково виконано порівняння часу послідовного та конкурентного виконання. Перевірка за допомогою Race Detector дозволяє контролювати відсутність станів гонитви під час роботи конкурентного коду.
