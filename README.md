## Короткі теоретичні відомості

### 1\. Структури, методи та неявна реалізація інтерфейсів

У Go відсутній механізм класичного успадкування класів (`class ... extends`). Замість цього використовуються структури даних (`struct`) та методи, прив'язані до конкретного типу через одержувач (**receiver**).

Інтерфейс у Go визначає контракт поведінки — перелік сигнатур методів. Якщо тип містить реалізацію всіх методів інтерфейсу, він вважається таким, що задовольняє цей інтерфейс **автоматично та неявно** (принцип качиної типізації: *«якщо щось ходить як качка і крякає як качка — це качка»*). Жодних ключових слів на зразок `implements` не існує.

// Оголошення інтерфейсу

type Greeter interface {

    Greet(name string) string

}

// Структура

type Bot struct {

    Prefix string

}

// Метод структури з value receiver, що неявно імплементує інтерфейс Greeter

func (b Bot) Greet(name string) string {

    return b.Prefix \+ ", " \+ name \+ "\!"

}

### 2\. Горутини та синхронізація через `sync.WaitGroup`

Горутина (`goroutine`) — це легковажний потік виконання, яким керує не ядро операційної системи, а вбудований планувальник середовища Go (GMP-scheduler). Початковий розмір стека горутини становить лише близько 2–4 КБ, що дозволяє запускати тисячі таких потоків паралельно без відчутних накладних витрат.

Для очікування завершення групи горутин використовується структура `sync.WaitGroup` з трьома основними методами:

- `Add(n)` — збільшує внутрішній лічильник активних задач на `n` (викликається **до** запуску горутини);  
- `Done()` — зменшує лічильник на 1 (зазвичай викликається через `defer` всередині самої горутини);  
- `Wait()` — блокує поточну горутину до моменту, поки лічильник не обнулиться.

var wg sync.WaitGroup

for i := 1; i \<= 3; i++ {

    wg.Add(1) // Збільшуємо лічильник до старту

    go func(id int) {

        defer wg.Done() // Гарантоване зменшення лічильника при виході

        // Виконання корисної роботи горутини

    }(i) // Обов'язкова передача аргументу за значенням

}

wg.Wait() // Очікуємо завершення всіх горутин

### 3\. Канали (`chan`) як безпечний транспорт даних

Парадигма конкурентності Go (CSP — Communicating Sequential Processes) спирається на принцип:

> *«Не спілкуйтеся, розділяючи пам'ять; натомість діліться пам'яттю, спілкуючись».*

Канал — це типізований потокобезпечний конвеєр для передачі даних між горутинами:

- `ch := make(chan string)` — небуферизований канал (блокує відправника, поки отримувач не буде готовий прийняти дані);  
- `ch := make(chan string, 10)` — буферизований канал (блокує лише у разі заповнення буфера);  
- `ch <- value` — надсилання значення в канал;  
- `val := <-ch` — вичитування значення з каналу;  
- `close(ch)` — закриття каналу відправником після закінчення надсилання даних;  
- `for item := range ch` — послідовне вичитування всіх елементів до моменту закриття каналу.

results := make(chan int, 5\)

// Відправник

go func() {

    for i := 1; i \<= 5; i++ {

        results \<- i \* 10

    }

    close(results) // Закриваємо канал, коли всі дані надіслано

}()

// Отримувач (вичитує до закриття каналу)

for val := range results {

    \_ \= val

}

### 4\. Вимірювання часу виконання

Для заміру швидкодії операцій використовується стандартний пакет `time`:

- `time.Now()` фіксує поточний момент часу;  
- `time.Since(start)` повертає тривалість (`time.Duration`), що минула від зафіксованої мітки часу.

## Постановка задачі

У клієнт-серверних архітектурах сервіси регулярно опитують зовнішні або суміжні API для перевірки їхньої працездатності (Health Check). Якщо робити це послідовно в одному потоці, опитування сотень сервісів займе неприпустимо багато часу.

Необхідно розробити консольну утиліту для **моніторингу доступності мережевих ресурсів (HTTP URL Health Checker)**, яка:

1. Зберігає перелік цільових адрес та виконує опитування їхнього стану;  
2. Фіксує результати кожного запиту: код відповіді (наприклад, 200 OK), час очікування та можливі помилки з'єднання;  
3. Демонструє еволюцію архітектурного рішення: від базової послідовної моделі до конкурентної обробки через горутини, синхронізацію та канали зв'язку.

## Завдання

Практична робота складається з трьох послідовних рівнів. Кожен наступний рівень базується на попередньому та розширює функціональність розроблюваного рішення.

### Рівень 1\. Базовий: структури, методи та послідовний моніторинг

1. **Ініціалізація проєкту:**  
   - Створити окрему робочу директорію для лабораторної роботи.  
   - Ініціалізувати Go-модуль за допомогою команди `go mod init <назва_модуля>`.  
   - Створити файл `main.go`.  
2. **Моделювання результатів:**  
   - Описати структуру для збереження результату опитування адреси:  
     - URL-адреса ресурсу (`string`);  
     - HTTP-статус код відповіді (`int`);  
     - тривалість виконання запиту (`time.Duration`);  
     - помилка у разі невдалого з'єднання (`error`).  
3. **Проєктування інтерфейсу та обробника:**  
   - Оголосити інтерфейс для абстрагування операції перевірки ресурсу (контракт має приймати рядок URL та повертати структуру результату).  
   - Створити структуру HTTP-клієнта з конфігурацією таймауту або внутрішнім полем клієнта.  
   - Реалізувати для цієї структури метод перевірки адреси (використати стандартний пакет `net/http` та функцію `http.Get` або метод `Do` власного клієнта `http.Client`).  
   - Усередині методу забезпечити точний замір тривалості виконання запиту за допомогою `time.Now()` та `time.Since()`.  
4. **Послідовний прогін:**  
   - У функції `main()` сформувати зріз (`slice`) із 4–5 різних адрес (включно з 2–3 реальними сайтами, наприклад `https://go.dev`, `https://github.com`, а також завідомо некоректним або неіснуючим доменом для тестування відловлювання помилок).  
   - У послідовному циклі опитати всі URL через інтерфейс та вивести у термінал статус, тривалість і текст помилки (якщо є).

### Рівень 2\. Конкурентний: горутини та захист спільного стану через Mutex

1. **Збереження функціональності Рівня 1\.**  
2. **Розпаралелювання запитів:**  
   - Замість блокуючого послідовного циклу організувати запуск перевірки кожного URL в окремій легковажній горутині за допомогою ключового слова `go`.  
   - Звернути особливу увагу на коректну передачу поточної адреси всередину анонімної функції горутини (уникнення замикання змінної циклу).  
3. **Координація завершення горутин:**  
   - Використати примітив синхронізації `sync.WaitGroup`, щоб головний потік програми дочекався закінчення опитування всіх серверів і не завершився завчасно.  
   - Забезпечити коректне збільшення лічильника перед запуском кожної горутини та виклик зменшення лічильника всередині горутини (бажано через `defer`).  
4. **Збір агрегованої статистики та ліквідація стану гонитви:**  
   - Оголосити спільну структуру для підрахунку підсумкової статистики (наприклад: загальна кількість перевірених адрес, кількість успішних відповідей зі статусом 200, кількість помилок).  
   - Оскільки горутини модифікують спільні лічильники одночасно, забезпечити захист критичної секції за допомогою `sync.Mutex` (методи `Lock()` та `Unlock()`).  
   - Перевірити програму на відсутність стану гонитви пам'яті за допомогою прапорця:  
       
     go run \-race .  
       
     Консоль не повинна містити жодних попереджень WARNING: DATA RACE.

### Рівень 3\. Просунутий: асинхронний збір результатів через канали

1. **Збереження функціональності попередніх рівнів.**  
2. **Перехід до передачі даних через канали:**  
   - Замість безпосереднього оновлення спільних лічильників через м'ютекс створити канал для передачі структур результатів із горутин.  
   - Після виконання перевірки горутина повинна відправити отриману структуру результату в цей канал.  
3. **Організація життєвого циклу каналу:**  
   - Запустити окрему допоміжну горутину-координатор, яка очікує завершення всіх обчислень через `sync.WaitGroup.Wait()` і одразу після цього безпечно закриває канал результатів за допомогою функції `close()`.  
4. **Обробка потоку результатів у головному потоці:**  
   - У функції `main()` організувати вичитування всіх результатів із закритого каналу за допомогою конструкції `for res := range resultsChan`.  
   - Здійснити підрахунок успішних/неуспішних результатів та вивести підсумковий структурований звіт моніторингу.  
5. **Порівняльний аналіз продуктивності:**  
   - Виміряти та вивести сумарний час роботи послідовного опитування (з Рівня 1\) та паралельного опитування (з Рівня 3).  
   - Зафіксувати кратне прискорення виконання завдання при конкурентному підході.

## Контрольні питання

1. Чим відрізняється неявна реалізація інтерфейсів у мові Go від явного контракту (`implements`) у таких мовах, як Java чи C\#?  
2. Яка різниця між передачею одержувача методу за значенням (`value receiver`) та за вказівником (`pointer receiver`)?  
3. Чому запуск 1 000 горутин у Go не призводить до вичерпання пам'яті комп'ютера, тоді як запуск такої ж кількості системних потоків ОС у Java чи C++ може спричинити збій?  
4. Що таке стан гонитви (race condition)? Як прапорець `-race` компілятора Go допомагає його виявляти?  
5. Для чого призначена структура `sync.WaitGroup`? Чому виклик `Add()` обов'язково має передувати оператору `go`?  
6. У чому полягає відмінність між блокуванням спільної пам'яті за допомогою `sync.Mutex` та передачею володіння даними через `chan`?  
7. Що трапиться, якщо спробувати надіслати дані у вже закритий канал або закрити вже закритий канал повторно?
